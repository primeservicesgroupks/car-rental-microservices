Turo-Style Car Rental Web App Using Microservices
===================================================

PROJECT GOAL
------------
Build a car-rental marketplace similar to Turo using microservices. The first version will be smaller than Turo but designed so it can grow.

1. SIMPLE ARCHITECTURE SUMMARY
------------------------------
Think of the platform as several small applications working together instead of one giant application.

Users -> Web/Mobile Frontend -> API Gateway/Load Balancer -> Microservices

Core services:
- Auth/User Service
- Vehicle Service
- Search Service
- Booking Service
- Payment Service
- Notification Service

Each microservice owns one main business responsibility and ideally its own data.

Benefits:
- Services can be developed independently.
- Services can scale independently.
- A failure in one service does not necessarily take down the entire platform.
- Easier to deploy and maintain individual components.

6. DATABASE DESIGN
------------------
Avoid one giant database shared by every service.

User Service -> Users DB
Vehicle Service -> Vehicles DB
Booking Service -> Bookings DB
Payment Service -> Payments DB

Initially, the databases can run on the same PostgreSQL server while remaining logically separated.

Vehicle pictures:
Vehicle Service -> Amazon S3 -> Vehicle Images

7. EXAMPLE USER JOURNEY
-----------------------
User searches for:
Location: Kansas City
Pickup: Oct 10
Return: Oct 13

Flow:
Browser
  -> API Gateway
  -> Search Service
  -> Vehicle Service
  -> Booking Service

Results might include:
- 2019 Toyota Camry - $48/day
- 2021 Honda Accord - $55/day
- 2020 Toyota Corolla - $43/day

8. BOOKING FLOW
---------------
User clicks "Book Now"

Booking Service
  -> Check vehicle with Vehicle Service
  -> Check availability
  -> Calculate/confirm booking
  -> Payment Service
  -> Payment provider
  -> Booking confirmed
  -> Notification Service
  -> Confirmation sent

Important distributed-system problem:
What happens if payment succeeds but the Booking Service crashes?

Later solutions:
- Events
- Message queues
- Idempotency
- Retries
- Saga pattern

9. SERVICE COMMUNICATION
------------------------
Synchronous communication:
- REST APIs
- One service calls another and waits for a response.

Examples:
GET /vehicles/123
POST /bookings

Asynchronous communication:
Booking Service
  -> BookingCreated event
  -> Message Queue
  -> Notification Service
  -> Analytics Service
  -> Owner Service

AWS technologies:
- SQS
- SNS
- EventBridge

10. AUTHENTICATION
------------------
Users should authenticate once rather than separately with every service.

Flow:
User
  -> Authentication
  -> JWT token
  -> Frontend
  -> API layer
  -> Microservices

Roles:
- RENTER
- OWNER
- ADMIN

Initially:
- FastAPI JWT authentication.

Later on AWS:
- Amazon Cognito can be considered.

15. DETAILED BUILD PLAN
-----------------------
PHASE 1 - Architecture and Repository
- Define MVP requirements.
- Define service boundaries.
- Create system architecture.
- Create repository.
- Create folder structure.
- Define API endpoints.
- Define database schemas.
- Define local development environment.

Main entities:
- User
- Vehicle
- VehicleImage
- Availability
- Booking
- Payment
- Review
- Notification

PHASE 2 - User Service
Build endpoints:
POST /users
GET /users/{id}
PUT /users/{id}
GET /users/{id}/profile

User database fields:
- id
- first_name
- last_name
- email
- phone
- password_hash
- role
- created_at

Learn:
- FastAPI
- Pydantic
- SQLAlchemy
- PostgreSQL
- REST APIs
- Validation

PHASE 3 - Vehicle Service
Endpoints:
POST /vehicles
GET /vehicles
GET /vehicles/{id}
PUT /vehicles/{id}
DELETE /vehicles/{id}

Vehicle fields:
- id
- owner_id
- make
- model
- year
- color
- license_plate
- daily_rate
- location
- status

Example:
{
  "make": "Toyota",
  "model": "Camry",
  "year": 2020,
  "daily_rate": 55,
  "location": "Kansas City"
}

Then add image upload to Amazon S3.

PHASE 4 - Booking Service
Booking fields:
- booking_id
- user_id
- vehicle_id
- start_date
- end_date
- daily_rate
- total
- status
- created_at

Booking lifecycle:
PENDING -> CONFIRMED -> ACTIVE -> COMPLETED

Possible cancellation paths:
PENDING -> CANCELLED
CONFIRMED -> CANCELLED

Critical requirement:
Prevent two renters from booking the same vehicle for overlapping dates.

PHASE 5 - Search Service
Search/filter by:
- Location
- Pickup date
- Return date
- Make
- Model
- Price
- Vehicle type

Example:
GET /search?location=KansasCity&start=2026-11-01&end=2026-11-05

Later:
- Add Redis caching.

PHASE 6 - Authentication and Authorization
Implement:
- Registration
- Login
- Password hashing
- JWT tokens
- Role authorization
- Protected endpoints

Permissions:
OWNER -> Can create/manage vehicles
RENTER -> Can create/manage bookings
ADMIN -> Can manage platform

PHASE 7 - Payment Service
Flow:
Booking
  -> Payment Service
  -> Payment Provider
  -> Payment Result
  -> Booking Service

Use sandbox/test transactions during development.

PHASE 8 - Event-Driven Architecture
Initial:
Booking -> Notification API

Improved:
Booking Service
  -> BookingCreated
  -> SQS/Event Bus
  -> Notification Service

Later consumers:
- Notification Service
- Analytics Service
- Owner Service

PHASE 9 - Frontend
Build pages:
- Home
- Login
- Register
- Search Cars
- Vehicle Details
- Checkout
- Booking Confirmation
- My Trips
- Owner Dashboard
- Add Vehicle
- Manage Vehicles

PHASE 10 - Docker
Create:
- Dockerfile for each service.
- docker-compose.yml.

Run:
docker compose up

Local environment should start the entire platform.

PHASE 11 - AWS AND TERRAFORM
Suggested Terraform structure:

terraform/
├── modules/
│   ├── vpc/
│   ├── eks/
│   ├── rds/
│   ├── s3/
│   ├── ecr/
│   ├── iam/
│   └── alb/
└── environments/
    ├── dev/
    └── prod/

Network:
VPC
├── Public Subnet AZ1
├── Public Subnet AZ2
├── Private App Subnet AZ1
├── Private App Subnet AZ2
├── Private DB Subnet AZ1

PHASE 12 - KUBERNETES AND CI/CD
Each service can have:
- Deployment
- Service
- ConfigMap
- Secret
- Horizontal Pod Autoscaler (HPA)

Example:

  -> Pod 1
  -> Pod 2
  -> Pod 3
  -> booking-service ClusterIP

Kubernetes can scale the number of pods as traffic changes.
